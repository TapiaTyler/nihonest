## Standalone implementation

- `article-metadata-producer.ts` reads the existing `articles.ts` family-spread assembly and each family's
  MDX import/tuple array through TypeScript's AST. Existing family/local tuple order remains the sole
  hand-maintained order inventory. Missing, duplicate, unregistered, unused, mismatched or unsupported
  registration inputs fail explicitly. Every canonical MDX file must be registered exactly once.
- Metadata uses the existing source splitter, followed by a restricted AST literal reader and the existing
  metadata schema. It never imports/compiles/executes MDX or evaluates JavaScript expressions. Ordinary
  object/array/string/number/boolean/null literals are supported; calls, identifiers, computed properties,
  spreads, duplicate/unsafe properties and interpolated templates are rejected. Metadata depth/size is bounded.
  Body syntax is not interpreted: reading metadata does not require N1's portable body grammar.
- `src/data/generated/article-metadata.ts` is checked in, with 97 schema-parsed records, defaults included,
  in web registration order. There are no timestamps, body prose, renderer references or second manual ID list.
  `scripts/build-article-metadata.ts` explicitly generates it atomically or checks expected bytes with `--check`.
  Generation runs the existing article/status/glossary/discovery/local-guidance/document reference validators
  before writing. The non-writing check rejects missing/stale output with a regeneration command.
- `createArticleMetadataCatalog` is a portable, injected selector factory. `article-metadata.ts` supplies the
  generated metadata and current discovery data, runs the same collection validators and exposes a
  `{ metadata }` facade with the existing selector names. All known/unknown ID, slug, group, journey and route
  semantics, including order and repeated journey articles, are preserved. No fake `Content` is returned.
- The facade, factory and generated metadata's transitive runtime dependency graph is tested: no React,
  Next, MDX, Node, dynamic loading or generator dependency. Zod is the permitted external runtime package.
  The Node/TypeScript source producer is separate and is not a runtime metadata consumer dependency.

No Japanese module, catalog, source-field rule, web registry, existing selector/consumer, package script,
Next/release/CI configuration or CMS code is edited. No browser or compilation savings are claimed.

## Freshness sequencing and remaining wiring

The checked-in module works in clean checkouts. A Vitest stale-output test recomputes expected bytes from
current source and registration order. Commands are explicit in this checkpoint:

`node --import tsx scripts/build-article-metadata.ts`

`node --import tsx scripts/build-article-metadata.ts --check`

Claude's agreed later freshness wiring: a release check and CMS regeneration on article save, under their
ownership rules. The existing entrypoints show one gap that needs coordination before consumer switching:
direct `next build` bypasses both Vitest and `release:check`. Checked-in output prevents a missing-file problem
in clean checkouts but cannot itself reject stale metadata after a manual edit. A non-writing Next build
freshness gate (or equivalent direct-build enforcement) is still needed. An npm `prebuild` hook alone misses
release, browser CI and CMS builds; a `pretest` hook misses direct Vitest runs.

Development saves also need coherent refreshed output. CMS creation currently coordinates an MDX file and
registration change, rolling back the new MDX on registry failure. Future regeneration must occur after a
successful canonical operation, preserve locks/dirty-file/refusal/rollback semantics and report a regeneration
failure without claiming the canonical save was rolled back when it was not. Body-only saves with unchanged
metadata do not change generated bytes. Watcher or refresh behavior is not implemented here.
