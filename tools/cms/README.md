# Local editorial CMS foundation

Run `npm run cms` from the repository root and open `http://127.0.0.1:4177`. Use that exact address: the server refuses other host names, including `localhost:4177`, to block DNS-rebinding requests. Set `CMS_PORT` to another local port if needed. Stop the process with Ctrl+C. The server binds only to `127.0.0.1` and is separate from the production Next.js application.

The start command includes a CMS-scoped fallback for a Windows host issue where Node's `os.userInfo()` fails before `tsx` starts. It handles only that specific OS lookup failure; it does not change the application's content behavior.

The CMS scans canonical English articles, FAQs, residence statuses, and glossary terms. The catalog has kind, status, and title/ID filters. It validates article metadata and supported body blocks, shows official source references and relationships, compares Japanese artifact revisions for articles, FAQs, residence statuses, and glossary terms, and reports the Git session (see below). Invalid files appear under “Files needing attention” without hiding the rest of the catalog. It offers a guarded body editor for `draft` and `needs-review` articles that have no `lastReviewedAt` date; an article that still carries a review date must first be moved between statuses in File Details, which removes the date. The structured editor can change FAQ questions and answers; residence-status summaries, purposes, activities, examples, and considerations; and glossary English definitions and usage context. Direct glossary entries can also change their English names. IDs, relationships, sources, Japanese fields, and structured residence decision-support rules remain read-only. A factual edit keeps an incomplete draft as Draft or returns other statuses to Editorial review, preserving historical approvals while requiring a new one for the new revision.

Article File Details lets you change status among `draft`, `needs-review`, and `archived`. FAQs and glossary terms support `draft` and `needs-review`; residence statuses also support `archived`. A separate Mark reviewed form for each kind requires your explicit approval, a review date, change and approval notes, and validation evidence. It writes `verified` and an immutable approval record for the exact resulting revision. Run `npm run editorial:audit` before committing. There are no source-resolution, Git staging, commit, push, or deployment actions.

Choose a content kind to narrow the category/topic filter: FAQ browse group, residence-status category, glossary topic, or article topic. The status and title/ID filters work across all kinds.

Structured records are shown with their complete stored data and source file. FAQs declare related articles rather than official sources directly, so review those linked articles and their source lists too. Structured content, status, and review actions check both the record revision and the whole source-file revision because several records share a TypeScript file. The CMS changes only the selected record's supported fields, preserves surrounding source text, and rejects an external change to a loaded data module until the CMS is restarted. A field diff appears before Save. Glossary terms created through shared builders accept per-term definition, context, status, and review-date overrides. Residence-status records retain their required `lastReviewedAt` field when moved out of Reviewed; the date alone is not an approval.

Structured records have Content, Linked Articles, Sources, and File Details tabs. The Content tab holds the editor and **Preview FAQ**, **Preview residence status**, or **Preview glossary term** control. The white preview surface updates as English fields change, including unsaved edits, and stays hidden until requested. It covers the editable content and major headings; it does not reproduce every website module. “Open full website view” opens saved content on the local web dev server for a final check. Status and human review controls live in File Details. Question-mark disclosures beside each editable content, status, and review field explain what belongs there. The review disclosures distinguish validation actually performed, resolved source-review IDs, and the explicit approval of the exact revision.

Article detail has Article, Linked Articles, Sources, and File Details tabs. For editable articles, the Article tab opens with the MDX editor, first formatting toolbar (H2/H3, bold, italic, lists, quote, links, component insertion, undo/redo), body/date change review, and Save. **Preview article** reveals the formatted article below the editor; it stays hidden until requested and updates from unsaved text. The toolbar writes supported MDX into the source textarea. A block-aware editor that lets you edit the formatted article directly is still required. Save checks the loaded SHA-256 revision again, validates the new blocks with the article schema, updates `updatedAt`, and atomically replaces only that article file. A 409 conflict requires a refresh; the CMS does not choose between versions. Embedded interactive components are shown as named placeholders. Use “Open full website view” with the web dev server on port 3000 to inspect their actual behavior. The File Details tab retains the raw MDX body for checking exact source text. Tabs support click and keyboard arrow/Home/End navigation.

Japanese translation state is `current` when the artifact's `sourceRevision` matches the record's English fields (the same rule as the translation catalog tests, from `src/domain/translation/translation-source-fields.ts`), `stale` when the English changed after the artifact was made, and `missing` when there is no artifact. The CMS never edits Japanese artifacts; hand stale or missing ones to the translation workflow in `content/translations/CLAUDE-TRANSLATION-REPORT.md`. Defaults that structured records rely on when a field is omitted (a residence status's review date, a glossary builder's status) are read from the data modules rather than copied into the CMS.

Article MDX and CMS-controlled structured status changes appear after Refresh. Source and Japanese translation registries (articles, FAQs, residence statuses, and glossary terms) are TypeScript modules loaded at process start, so restart the CMS after changing those files externally. Translation currency shown by the CMS is only as current as those loaded modules. The optional formatted preview is not a full Next.js page preview; exact interactive component rendering remains a later slice.

## Git session

When the CMS starts it records the worktree, repository, branch, starting commit, and every file that already has uncommitted changes, and prints them in the terminal. The Working tree panel shows the same identity and groups changed files into those written by this CMS session, those already changed before it started, and those changed by another editor or agent during it; open a file to see its diff against HEAD. The CMS refuses to write a file that was already dirty when it started (HTTP 423), so its edits never mix with unreviewed work in the same file. Commit or set those changes aside and restart the CMS, or run it from a separate worktree. It also refuses all writes if it cannot read the Git checkout, and warns if the branch or commit changes after it started; restart it in that case. The CMS never stages, commits, pushes, switches branches, or discards changes. For concurrent editing with other agents, run the CMS from a dedicated worktree with its own dependencies so CMS code, source registries, and content files come from the same checkout; the revision checks catch collisions in a shared checkout, but a separate worktree is the reliable isolation boundary.

## Checks and release gates

Run the focused checks with `npx vitest run tools/cms`, `npx tsc --noEmit`, and `npx eslint scripts/cms.ts tools/cms`. The CMS tests include a source-level production boundary check. Before a release, stop the dev server (it shares `.next`), then run `npm run build` and `npm run cms:check-build`, which fails if any CMS code or endpoint marker appears in the production output.

## Acceptance status

Against the release gates in [the requirements](../../docs/LOCAL-CMS-REQUIREMENTS.md) §11:

| Gate | Status |
|---|---|
| Representative article and structured-record edit through the local flow | Done for article bodies and supported structured fields. |
| Article formatting controls with lossless MDX round trip | Partial: toolbar writes MDX into the source editor; the block-aware formatted editor and round-trip tests against real articles are not built. |
| Accurate status and translation-staleness display | Done for articles, FAQs, residence statuses, and glossary terms. Municipality guidance and other catalogs are not in the CMS yet. |
| No data loss with a pre-existing dirty tree or concurrent edit | Done: revision checks with atomic replacement, and refusal to write files that were dirty at session start. |
| Blocked stale approval and explicit human approval path | Done: approvals bind the exact revision, and edits return records to editorial review. |
| Meaningful accessibility checks | Partial: keyboard tabs, labels, and disclosures exist; no automated or assistive-technology audit has been run. |
| Production build contains no CMS endpoint | Source check in the test suite; the build-output check (`npm run cms:check-build`) must be run as described above. |

Not built yet (requirements §4, §8, §9): running validation checks from the interface, dependency and impact views (source-to-dependent, content-to-source, translation handoff list), search results that explain why they matched, the local activity log and crash-recovery drafts, isolated worktree creation from the interface, commit-message preparation and selected-file staging, and adapters for the remaining catalogs (municipality guidance, sources, annotated documents, journeys, and article groups). Full website-component preview and richer structured metadata editing are also still to come.
